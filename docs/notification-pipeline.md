# 公演取得とLINE通知の検証記録

## 運用と確認方法

- 本番同期は5分 cron を維持する。FANY は出演者ごと、劇場は劇場ごと、他チケットサイトはサイト・出演者ごとに独立して処理する。ジョブ内の通知処理は単一の消費側が担当する。GitHub Pages は別のワークフローで、最後にコミットできたカタログを再生成・公開する。LINEの一時失敗でPagesを止めない。
- 本番の状態は Git の `line-notification-state` ブランチに保存する。既存の2つの通知履歴 JSON は保管し、移行時の既存掲載と照合に使う。移行時に掲載済みの公演は `legacy` で、API受理を意味しない。日付の裏付けがない旧履歴については、以前の正確なソースキーを重複防止のため保守的に扱う。
- `source_result` で取得元と所要時間、成功・失敗、取得件数を確認する。`schedule_interval` は直前の定期ジョブの処理開始から今回の処理開始までの秒数。GitHub Actions のスケジュール作成時刻・runner待ちは Actions 一覧で別途確認する。
- `event_decision` に公演キー、公式ID、初回観測、判定時刻、抑止理由を出力する。`line_result` にリクエストID、HTTPステータス、試行結果、ダイジェスト詳細掲載キーが出る。HTTP 200 はLINE APIが受理したことを表し、端末への着信証明ではない。再試行が409と受理済みリクエストIDを返した場合は、初回の正確な受理時刻を未確認として保存する。
- リクエスト本文とLINEリトライキーをGitに保存してから送信する。保存失敗時は送信を開始しない。送信後に状態保存が失敗した場合、次回は同じキーと本文で再試行する。24時間経過した応答不明のバッチは `reconciliation_required` に保留し、自動再送しない。拒否が全試行で確定している場合のみ新しいキーで再試行できる。
- 過去のコードで実際に未送信だったと独立した証拠で確定した将来公演は、同期ワークフローの手動実行で `requeue_record` に状態JSONの `records` の正確なキーを指定する。`requeue_evidence` に個人情報を含まない照合根拠を入力する。最初は `requeue_confirm` をオフにしてレビューし、根拠が確認できた場合のみオンで送信する。送信成功・通知待ち・送信失敗の同一公演が新状態に存在する場合は再登録を拒否する。「トイレッツ」はこの調査で未送信と確定していないため、再登録対象にしていない。

## 検証条件と費用

全10劇場の公開HTMLおよび3種類の月表示スクリプトを確認し、実際のChromium上で模擬フィードを返して、年月とIDの照合を通過することを確認した。公開ページが通常表示のために要求するレスポンスのみを使用し、フィードへの独自リクエストは本番コードに追加していない。フィードの利用条件本文と実レスポンスの取得は現環境のアクセス制約により未確認。FANYや劇場フィードの本番接続状況と送信ログ本文はマージ前の調査では確定できていない。個人名義の照合には既存の個人出演レーダーの公認プロフィール由来の名義を共用する。追加の確認済み名義は出演者設定の `aliases` に登録できる。

有料サービスは不要。公開リポジトリの標準GitHub-hosted runnerと既存のLINE連携を使う。非公開化やrunner変更時はActions無料枠を再計算する。取得元別に先行通知するため、同じ同期で複数の取得元に新着がある場合はLINE通知数が従来より増える可能性があり、現行契約の実消費は本番ログとLINE管理画面で確認する。5分ごとにジョブが起動し、対象ソースの取得・判定・受理が1〜2分以内なら、公開からおおむね0〜7分が目安。GitHubのスケジュール起動遅延、取得元の403やタイムアウトがある場合はこの範囲を超える。

実装前の11/25 JSTの最新観測では、定期実行の作成時刻は06:28:44、13:26:54、23:43:53で、連続実行の間隔は6時間58分10秒と10時間16分59秒だった。処理時間は1分44秒〜2分04秒。マージ前の観測値であり、新処理の速度は本番環境で未計測。

## マージ前の読み取り専用検証

GitHub の [既存の手動劇場ワークフロー](https://github.com/wani01-dot/-02/actions/workflows/theater-probe.yml) を開き、**Run workflow のブランチに `codex/notification-pipeline` を指定**する。既存パスを使うことで、デフォルトブランチに新規ワークフローを追加せず検証できる。**マージ前の `main` にある旧定義はLINE送信処理を含むため実行しない。** このブランチの手動検証では既存のLINE設定を渡さず、checkoutの資格情報を保持せず、GitHub権限も `contents: read` に限定する。取得と新着判定は本番関数を使い、判定状態はメモリ内だけで保持する。

- `probe_source_result` は10劇場とFANYの3組それぞれについて、成否・UTCの開始/完了時刻・取得秒数、成功時の対象年月・組別件数・候補判定秒数を出す。劇場の公式掲載全件数、3組対象の公演数、出演者別の件数は分けて記録する。FANYの総掲載数は未集計で、ログの公演数は取得できた対象組の公演数。
- `probe_official_show` と `probe_show` は、公式公演ID、日時、タイトル、出演者欄、参照URLを出力する。
- `probe_review` は [12公演・13出演者レコード](theater-review-candidates.json) の保存行と公式照合結果を並べる。`cast_differs_review_required` は公式ページの出演者欄が完全かを人が確認する候補。`not_found`、`outside_verified_months`、`cast_unpublished`、`source_unavailable` などは掲載維持。照合処理は自動で修正・除外しない。
- `probe_summary` は成功・失敗と仮のバッチ数を集約する。1ソースでも失敗するとジョブを失敗表示にするが、全対象を確認した後で終了し、ログはアーティファクトに一定期間保存する。仮のバッチ数はチェックアウト時点のカタログ・旧通知キーから推定し、本番の送信履歴や送信通数ではない。

### スケジュールの再調査

| 定期実行（JST） | 直前の定期実行との間隔 | 実行作成からジョブ開始 |
| --- | ---: | ---: |
| 11/25 06:28:44 | 9時間51分16秒 | 4秒 |
| 11/25 13:26:54 | 6時間58分10秒 | 3秒 |
| 11/25 23:43:53 | 10時間16分59秒 | 4秒 |

公開画面では4件とも成功し、前のジョブが何時間も実行・待機し続けた形跡はない。公開一覧に実行が現れなかった各5分枠の理由は、GitHub内部のトリガー記録にアクセスできないため未確認。GitHubは混雑時のスケジュールの遅延や破棄を明記しているが、今回の特定原因としては断定できない。

完全無料の範囲では、まず混雑しやすい正時を外して既存の発見・配信ジョブと重ならない `4-59/5 * * * *` を比較候補にする。通知とPagesの分離、手動取得検証の競合グループ分離も維持する。変更前後の実行作成間隔とrunner開始待ちを別々に記録し、5分以内・10分以内の割合、最大間隔を比較する。現在の `*/5` 自体は今回変更していない。GitHubの無料スケジュールに厳密な5分間隔の保証はない。重複cronの追加はリクエスト数と競合を増やすため、最初の手段にはしない。

### LINE送信通数の試算

11/19 00:00〜11/26 00:00 JSTの本番保存コミット27回について、各コミット直前の `events.json` と `theater_events.json` を比較した。当日以降に増えた行は劇場137、TIGET31。通常サイトを一括、劇場を一括と仮定する旧方式では24バッチ。劇場別・チケットサイトと出演者別に分ける案では35バッチとなり、差は11、約46%増。最大は1回に6バッチだった。これは保存差分を仕分けした試算で、送信ログ、重複除外後の実測値、5分間隔が回復した場合の予測ではない。この期間の保存差分にはFANYが含まれない。

再取得が安定し他の取得元も毎回新着となる場合は、1同期につき最大22取得単位がそれぞれ1バッチを作り得る。1人に送る場合でも無料枠を超える可能性がある。現契約・送信先の人数・他の配信を含む月間消費は管理画面の確認が必要。仮に月200通、送信先1人、観測週と同じペースなら35×30÷7で約150通/月だが、その前提では月間超過を保証できない。

速度を抑えずに通数を減らす候補は、先頭の新着を10〜20秒だけ待って、その間に完了した取得元を同じFlexに集約する方式。さらにLINEの利用量を参照して、設定した予算の残りが少ない場合だけ集約を強める。送信枠がない場合は取得とカレンダー更新を継続し、通知待ちとして保持する。通知デザイン・LINE送信先・本番の送信制御は、この追加検証では変更していない。

## 実行 #6 の成果物による再確認

218件の重複元はすべて公式ID導入前の劇場レコードで、その全行に実行時点の旧劇場通知キーがあった。新表示では旧履歴キーありと、掲載だけ確認できた状態を分ける。旧キーだけからLINE受理・着信の有無を判定することはできない。自動再通知の対象には追加していない。
